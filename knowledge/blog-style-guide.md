# 博客风格指南

更新：2026-11-02。目的：保留同一个作者的声音，同时让不同题材有合适的结构。

## 先选风格

| 代号 | 风格 | 适用内容 | 主线 | 常用版式 |
| --- | --- | --- | --- | --- |
| A | 实践教程 | 部署、工具配置、完整操作流程 | 为什么做 → 按序操作 → 验证 → 排障 | `tech` |
| B | 排障速记 | 一个具体报错或故障 | 现象 → 检查 → 原因 → 修复 → 验证 | `tech` |
| C | 生活叙事 | 参赛、校园、出行、日常记录 | 起因 → 场景 → 心情变化 → 真实收尾 | `story` |
| D | 赛后复盘 | 比赛总结、项目回顾、学习反思 | 目标与结果 → 关键片段 → 原因 → 改进 | 按叙事或分析重点选择 |

一篇以一种主风格为主，可以吸收另一种的少量特点。例如教程开头留两段经历，复盘用一张表列改进计划，不必把所有结构都拼进去。

## 共同的作者声音

第一人称、自然口语、具体细节，像把自己做过的事讲给朋友听。可以承认不会、写一点自嘲，但随后要给出发生了什么或下一步做什么，不能整篇都在渲染“我很菜”。

现有文章常用“从……说起”的起笔、短段落、少量引用和删除线；这些是可选手法，不是必须逐条模仿的公式。继续保留轻松感，同时减少重复感叹、同义反复、密集加粗和结尾口号。

本次明确的编辑方向：**先理顺逻辑，再减少字数；技术表述准确，避免为了补充所有例外而不断扩写。** 保留会影响读者操作和判断的边界，次要细节交给官方链接。

## A：实践教程

样本：`content/posts/2026/Blog Questions（2）.md`，即《博客的托管、域名和图床》。

结构建议：

1. 用真实起因和最终效果开头，涉及多服务时给一条流程图。
2. 按操作依赖推进，每节回答“从哪里进入、点击什么、值从哪里获取、每个字段填什么、怎样保存、怎样验证”。面向新手时不能把这条链路压缩成“按提示配置”。
3. 配置字段用表格，顺序操作用编号；原理只解释到足以完成判断。
4. 排障集中放在流程后面，费用与维护放到末尾。

精简以删除重复解释为主，不能省掉关键操作。遇到多个分支，先完整写通本文使用的一种，再用小表格或短段说明其他选择；例如域名教程应区分 `blog`、`www`、`@`，以及 CNAME 的域名目标与 A 记录的 IP，避免让新手把备选方案全部照填。

语气：清楚、轻松，教程本体少插叙。避免“正确姿势只有一种”“照抄就一定成功”之类结论。

示例语感：

> 本地跑通后，还差一个能让别人打开的地址。这次先部署博客，再把域名和图片接上。

## B：排障速记

样本：`content/posts/2026/blog-questions.md`，即《小白部署尝试的开源博客》。参考它从实际报错切入的方式，不沿用重复的“执行 / 然后 / 说明”和多次相同警告。

结构建议：

1. 给出环境、操作和原始报错，只截有用的日志。
2. 先用检查命令缩小范围，再说明确认的原因；猜测要单独标明。
3. 给出最小修复步骤，随后用命令输出或实际行为验证。
4. 必要时留一句防止再次踩坑的提醒，不扩写成完整产品教程。

语气：直接、短，吐槽限开头或转折。没有实际运行过的修复办法，不能写成已经验证成功。

示例语感：

> `git push` 卡在公钥认证。先确认远程仓库走 SSH，再检查本机是否有对应的密钥。

## C：生活叙事

样本：`content/posts/2026/BiSai.md`，即《第一次参加御网杯，有点激动》。

结构建议：

1. 从一个明确时刻、念头或小场景进入。
2. 按时间或情绪变化选几个片段，不必把所有行程都记下来。
3. 用真实动作和细节承载心情，赛事规则等背景只留理解故事需要的部分。
4. 停在真实感受或接下来的行动上，不强行升华。

语气：有现场感，允许一点紧张、玩笑和颜文字。只把材料中确认的对话作为原话；缺细节就少写，不编造。

示例语感：

> 去年看到学校的获奖消息时，只是想过自己能不能试试。今年轮到收拾电脑，准备出发了。

## D：赛后复盘

样本：`content/posts/2026/yuewangbei.md`，即《第一次参加御网杯，下次还来》。保留前后篇呼应和具体片段，并加强“原因与改进”，不只复述结果或表达感慨。

结构建议：

1. 先交代目标和实际结果，系列文章用一句话接上前篇。
2. 选两三个影响结果的片段，说明当时怎么做、哪里有效或卡住。
3. 分清准备、执行、协作和外部因素，不把结果全部归结为运气。
4. 给出少量可执行的改进：练什么、怎么练、怎样确认有进步。

语气：坦诚、克制。奖项只是结果，复盘的价值在于解释过程；没有依据时不要替队友归因，也不要编一个漂亮的成长结论。

示例语感：

> 奖拿到了，但这次暴露的问题也很明确。接下来想把比赛里卡住的部分单独拆开练。

## 下次如何指定

请求里提供“风格代号 + 题目或素材 + 目标篇幅 + 必须保留的细节”即可，例如：

> 用 B 写这次 Nuxt 构建报错，800 字左右，保留报错原文和验证命令；没确认的原因单独标出来。

> 用 D 整理这份比赛记录，1200 字左右，开头接上一篇，多讲改进，少一点抒情。

以上示例和篇幅是选择方式，不是所有文章的固定要求。用户已指定风格时直接执行；题材足够明确时可以据此选择，并简短说明。素材同时适合叙事和分析、且取向会明显影响文章时，再让用户选主风格。
